# 安定運用フェーズ（v1.4.0～）の運用ガイドライン

本ドキュメントは、v1.4.0（言語化ファースト完全実装）リリース後の安定運用フェーズにおける、システムの運用・保守・機能拡張に関するルールを定めます。

## 1. ブランチ・リリース運用ルール（Hotfix & Feature）

安定運用フェーズでは、本番環境（`main` ブランチ）の安定性を最優先とし、以下のブランチ戦略を徹底します。

- **新規機能開発 (Feature)**
  - 必ず `feature/*` ブランチを作成し、開発環境（Worktree） (`video-insight-spec-dev`) で実装・テストを行う。
  - テスト (pytest) が 100% PASS することを確認した上で `main` へマージする。
- **バグ修正 (Hotfix)**
  - 緊急のバグ修正は `hotfix/*` ブランチを作成して対応する。
  - 修正後は速やかに `main` にマージし、パッチバージョン（v1.4.1等）を付与してリリースする。

## 2. 本番ディレクトリの保全ルール

本番安定版（Git 親リポジトリ）（`D:\AI_スクリプト成果物\video-insight-spec`）は、常に `main` ブランチの最新リリースバージョンを保持するクリーンな状態を維持します。

- **直接編集の禁止**
  - 本番ディレクトリ内の追跡対象ファイル（ソースコード、設定ファイル等）を直接編集してはならない。
  - 開発作業は必ず開発環境（Worktree）（`video-insight-spec-dev`）で行うこと。
- **変更の反映**
  - 開発環境で `main` にマージ後、本番ディレクトリ側で `git pull origin main` を実行して変更を反映する。
- **Untracked File の管理**
  - アプリの起動スクリプト（`run_prod.bat`）や一時出力ファイル（PDFレポート等）は Untracked 状態として許容するが、Git 管理下には追加しない。

## 3. 営業支援・補助運用（無料1本解析）

安定運用フェーズにおける営業利用の最小導線として、商談時の「無料1本解析」フローを用意しています。これは新機能追加ではなく、既存VISの価値（品質診断・改善提案）を最小構成・手動で回すための補助運用です。

**位置づけ・商談フロー**:
本フローは、「レポート納品」ではなく「商談時のダッシュボード実演（デモ）」を標準とします。
1. 動画受領とスクリプト実行
2. 商談にてダッシュボード画面を共有
3. 「品質診断」タブで現状を説明
4. 「改善提案」タブで次のアクションを提案
5. 必要に応じて後送資料（`report.md`）を送付

- **詳細運用手順・商談前チェックリスト**: [FREE_TRIAL_ONE_VIDEO_OPERATION.md](FREE_TRIAL_ONE_VIDEO_OPERATION.md) を参照してください。

**無料1本解析モードと通常モードの使い分け**:
ダッシュボード起動時に環境変数 `VIS_MODE` を指定することで、以下の2つのモードを切り替えます。
- **通常モード（デフォルト）**: `streamlit run streamlit_app/app.py`
  既存のデモ用5講座が表示されます。
- **無料1本解析モード**: `$env:VIS_MODE="free_trial"` してから `streamlit run streamlit_app/app.py`
  無料1本解析の対象動画が自動選択されます。顧客との商談デモ時は必ずこのモードを使用してください。

## 4. Backlog（今後の機能拡張・課題リスト）

v1.4.0 時点での残課題および今後の拡張予定（Phase 5以降）は以下の通りです。着手時は本リストから優先順位を判断します。

### 高優先度 (High Priority)
1. **統合テスト（E2E）の実装**
   - Streamlit UI の操作から AI 呼び出し、最終的な画面描画までのフロー全体を自動検証するテスト環境の構築。
2. **UI/UX の微調整**
   - AI による状態診断出力の「結論・課題・次アクション」を、より視覚的に目立つカード型UIやハイライトボックスで表示する改修。

### 中優先度 (Medium Priority)
3. **GitHub Actions による CI/CD 構築**
   - Push時および PR作成時に `pytest` を自動実行し、テスト結果をフィードバックする CI パイプラインの導入。
4. **Config システムの拡張**
   - ビジネスラベルが50個を超えた場合を見据え、`diagnostic_config.yaml` を複数ファイルに分割・モジュール化する対応。

### 低優先度 (Low Priority)
5. **カバレッジ測定の導入**
   - `pytest-cov` 等を導入し、テストカバレッジの可視化と維持・向上を図る。
