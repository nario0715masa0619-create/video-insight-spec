# VIS 開発初期整備計画書 (DEV_HARDENING_PLAN)

## 1. 目的
本計画書の目的は、VIS（Video Insight Spec）プロジェクト本来の形への整備を安全に進めるため、現状の把握、実行経路の明確化、および具体的な整備タスクの優先順位付けを行うことです。いきなり大規模な改修を行うのではなく、堅牢な土台を構築することを主眼としています。

## 2. デモ環境と開発環境の分離方針
現在のローカル環境は以下の運用ルールで厳密に分離されています。
- **デモ実施環境 (`video-insight-spec`)**: `demo.bat` を使用し、商談・デモ専用として無傷のまま保持する。
- **開発・整備環境 (`video-insight-spec-dev`)**: 今後の修正、検証、機能追加、および本計画の実施はすべてこちらの worktree 上で行う。

## 3. VIS がちゃんと動く状態の定義
VISの健全な動作とは、以下が満たされている状態を指します。
- `insight_spec_{id}.json` を揺るぎない「正本」として扱うこと
- ダッシュボードが `insight_spec` から安定して動的集計・表示できること
- 必要な環境変数・依存関係（Python / `.env` など）が再現可能にセットアップできること
- 経営者向けサマリーなどの中間ファイルの生成ロジックの所在と CLI / バッチ経路の入口が明確であること
- `OPENAI_API_KEY` が未設定であっても、ダッシュボードがクラッシュせず劣化モード（警告表示あり・機能制限）で成立すること
- デモと本整備の役割分離が維持されていること

## 4. 現在の実行経路一覧
現在の動作経路の棚卸し結果は以下の通りです。

### デモ用起動経路 (すでに動く)
- 起動元: `demo.bat`
- 実行コマンド: `streamlit run streamlit_app/app.py`
- 状態: `%USERPROFILE%\.video-insight-spec\.env` に依存してダッシュボードが安定起動する（確認済）。

### ダッシュボード経路 (すでに動く・一部弱点あり)
- 既存データ読み込み: `streamlit_app/data_loader.py`
- `insight_spec` 直接集計: PR #27、PR #29 にて是正・稼働済み。
- AIサマリー: `streamlit_app/narrative_engine.py` によりキー存在時のみ動的生成。

### CLI / バッチ経路 (動作未確認・整備要)
- 各スクリプト（`converter/executive_summary_formatter.py` など）の稼働状況や、何をどのAPI（`YOUTUBE_API_KEY` / `GEMINI_API_KEY`）を使って生成するかの流れが散在。
- 入力と出力の一貫した通しテストが不足しており、壊れやすい状態であると推測される。

## 5. 主たる正本データと補助データの整理
- **正本**: `insight_spec_*.json` (すべての洞察、スコア、メタデータの源泉)
- **補助(非必須)**: `executive_report.json` (キャッシュ的ファイル。存在しない場合は `insight_spec` から動的生成される)

## 6. 既知の強み
- ダッシュボードは `insight_spec` 直接集計で表示でき、フェイク値のない正確なデモが可能。
- ユーザーホームディレクトリの `.env` 運用により、セキュアで環境依存の少ないセットアップ基盤が整っている。
- AI API 未設定時のフォールバック機能が実装済み。

## 7. 既知の弱み
- `load_executive_report()` において、中身が空 `{}` などの不完全なJSONに対するフォールバック検証が甘い（例外キャッチ依存）。
- バッチ・CLI経路（データ生成側）のドキュメントと実態の乖離がある可能性が高く、再現性が未検証。

## 8. 整備優先順位
「デモを守りながら本体価値を強くする」観点から、以下のレイヤーで優先順位を設定します。

### A. すぐやるべき整備
- 正本データ定義の整理と浸透（チーム内合意事項の明文化）。
- 不完全 JSON fallback（バリデーション強化）の実装。
- 実行経路（特にCLI / バッチ経路）の再現確認。

### B. 中期でやる整備
- バッチ生成ライン（新規データ取得〜 `insight_spec` 生成）の再現性向上とテスト。
- 各 JSON ファイルのスキーマ検証（JSON Schema等）の導入。
- エラーハンドリングの全般的な強化とログ基盤の整備。

### C. 将来的な強化
- 動画内の細かい時間位置精度や、視聴維持率など実データの詳細統合。
- 外部API化、Slack連携などのシステム外部展開。

## 9. 次に着手すべき具体タスク
1. **不完全 JSON への fallback 強化**: `data_loader.py` 内で、`lectures` キーがない等の空 JSON に対して再集計へ回す堅牢化を行う。
2. **バッチ経路の再現確認**: `converter/` や `scripts/` にある主要データ生成スクリプトの入出力を洗い出し、ローカルで通し実行が可能か確認する。
3. **環境構築手順書の検証**: クリーンな環境から `bootstrap_user_env.ps1` と `requirements.txt` を用いて、正しく環境が再現できるかのリハーサル。

## 10. executive_report.json 廃止方針

### 1. 方針
- `executive_report.json` は非正本であり、今後の主経路に使わない
- 正本は `insight_spec_{id}.json` である
- 新規実装・改修実装では `executive_report.json` を一切参照しない
- 既存の残存参照は減らす方向で扱い、段階的に縮小して最終的に削除する
- 一時的な fallback / 互換処理が残っていても、それは恒久設計ではない

### 2. 完了条件
- ダッシュボードが `executive_report.json` を一切参照せず動作する
- バッチ / CLI が `executive_report.json` を一切参照せず動作する
- AI分析・集計・個別動画表示が `insight_spec_*.json` のみで成立する
- コードベース内の `executive_report.json` 参照がゼロになる
- ドキュメントでも `executive_report.json` を前提にしない

### 3. 実装ルール
- `executive_report.json` の新規生成コードの追加は禁止
- `executive_report.json` への新規参照追加は禁止
- 既存コードを触る場合、その箇所の `executive_report.json` 依存は可能なら除去する
- 欠損値を 0 や仮値で埋めて延命しない
- 判断に迷ったら `insight_spec` だけで成立する設計を優先する

### 4. 開発運用メモ
- 今後の AI チャットや自動化支援への指示でも、この方針を前提にする
- `executive_report.json` は段階的縮小対象ではあるが、最終ゴールは参照ゼロである
- `executive_report.json` を復活・再設計したい場合は、実装前に別途スキーマ・責務・生成タイミングを定義すること
- それまでは一貫して「縮小・撤去対象」として扱う
